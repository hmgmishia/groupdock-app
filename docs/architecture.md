# GroupDock の構成・実装方針・最適化

この文書は「どう作っているか」「何を最適化したか」「何が残っているか」「リッチな見た目を保ったまま軽くする考え方」をまとめる。
数字は 1 台の Mac（Apple Silicon・4K・Music と Chrome 起動中）での実測。**実測**と**推測**は分けて書く。

## 1. 全体像

macOS の Dock の代わりに、画面の端へ浮かぶ「帯」を出すメニューバー常駐アプリ。Swift / SwiftUI / AppKit のみ。外部ライブラリなし。

| 層 | 主なファイル | 役割 |
|---|---|---|
| 状態 | `Model.swift`（`Store`・`Prefs`・`DropState`） | グループ・残すアプリ・設定・履歴・実行中・バッジ。保存と復元 |
| 配置（純粋関数） | `StripLayout.swift`（`StripLayout`・`BubbleLayout`・`GridMetrics`）、`TileHitTest.swift`、`BubblePlacement.swift` | 状態から枠を計算する。描画結果は読まない |
| 描画 | `DockView.swift`、`WidgetFaceView.swift`、`NowPlayingView.swift`、`HistoryView.swift`、`InstanceView.swift` | 計算済みの枠に従って描くだけ |
| ウィンドウ | `DockWindow.swift`（`DockPanel`・`DockWindowController`・`GroupBubbleController`） | 非アクティブ化パネル、ドラッグ、右クリック、自動で隠す、ホバーの札 |
| 外部との接点 | `SystemDock.swift`、`Watchdog.swift`、`DockMenu.swift`、`NowPlaying.swift`、`Helper/gdnowplaying.m`、`Launcher.swift` | 標準 Dock の制御、再生中、アプリ定義メニュー、起動・終了 |

### 純粋関数と描画を分ける理由（最重要の方針）

設計の規則「配置は状態から計算する」。SwiftUI の `GeometryReader` や `PreferenceKey` で測った寸法を `@Published` に書き戻す作りは、
更新ループと `EXC_BAD_ACCESS`（AttributeGraph）を起こした。そこで次の形に作り直した。

1. `Store` の状態（件数・アイコンの大きさ・余白・名前の表示）だけから、枠を純粋関数で計算する。
2. SwiftUI は計算済みの枠に `offset` と `frame` で置くだけ。
3. ウィンドウの大きさ・当たり判定・ドラッグの挿入位置も、同じ計算結果を使う（描画と判定がずれない）。

効果は 3 つある。クラッシュが無くなった。`tests/run.sh` で、画面を出さずに配置を検査できる。描画のたびに寸法を測り直さないので軽い。

## 2. 主な設計判断

| 判断 | 理由 |
|---|---|
| 帯は `.nonactivatingPanel`、`.floating`、全スペース・全画面に出す | 他のアプリの操作を奪わない |
| ドラッグ・右クリック・ホイールは `DockPanel.sendEvent` で受ける | SwiftUI の `.draggable` / `.contextMenu` はこのパネルで安定しない |
| ドラッグ中の絵は、描いているタイルをそのまま写して動かす | 見た目が一致し、別の絵を用意しない |
| 標準 Dock は「自動で隠す＋待ち時間 1000 秒」で隠す | 停止・終了時に必ず戻す。`Watchdog` が固まりを見て戻す |
| 実カーソルを動かす検証はしない | オーナーの操作を奪うため。画面確認は描画の書き出しとアクセシビリティの読み取りで行う |
| 再生中は Apple 署名の `/usr/bin/perl` に補助ライブラリを読み込ませる | macOS は MediaRemote の情報を Apple 署名のプロセスにしか返さない（実測）。読み取りと再生操作だけで、通信もファイルの書き込みもしない |
| アプリ定義の右クリック項目は標準 Dock のメニューを AX で読む | 他に取る方法が見つからない。読む間、標準 Dock のメニューが約 60ms ちらつく（仕様として受け入れ済み） |

## 3. 更新のしくみ（タイマー）

| タイマー | 間隔 | 内容 |
|---|---|---|
| `Store.timer` | 3 秒 | 実行中アプリの一覧、インスタンス数。2 回に 1 回（6 秒）は応答・ウィンドウ数の確認。10 回に 1 回（30 秒）はアイコンの更新確認 |
| `widgetTimer` | 秒まで出す時計・日付があるときだけ 0.25 秒、無ければ 1 秒、ウィジェットが無ければ 5 秒 | ウィジェットの文の更新判定（実際の更新は種類ごとの間隔で絞る）と、再生中の取得の判定。設定が変わると張り直す |
| `badgeTimer` | 5 秒 | 標準 Dock の未読バッジ（AX） |
| ライブラリ監視 | 1.5 秒 | 外部ウィジェット JSON の変更 |
| `Watchdog` | 1 秒 | 固まりの検出 |
| ホバー・自動隠し | 自動で隠す設定のとき、または帯の近くにカーソルがあるときは 0.2 秒、離れていれば 0.5 秒 | カーソル位置の判定、名前の札 |
| 再生中の取得 | 再生中 3 秒・停止中 6 秒 | `perl` を起動して補助ライブラリを呼ぶ。操作したときは即座に読む |

値が変わらないときは `@Published` に書かない（`if new != old`）。描き直しは変化があったときだけ。

## 4. 最適化の記録

### 4.1 実施済み

| 内容 | 効果 |
|---|---|
| 配置を純粋関数にして、寸法の書き戻しをやめた | クラッシュ解消。描画のたびの再測定が無くなった（推測：CPU も減った。単独の数字は取っていない） |
| グループを開くときの名前欄の全文選択と `ps` 実行をやめた（普段は文字、ダブルクリックで入力欄。`ps` は押したときだけ） | 開くときの引っ掛かりが無くなった |
| 実行中アプリの巡回を 3 秒、バッジを 5 秒、再生中を 3/6 秒に | 重い呼び出し（`ps`・AX・`perl` 起動）を間引いた |
| 応答・ウィンドウ数の確認を 6 秒に 1 回、アイコンの更新確認を 30 秒に 1 回に | 同上。見た目への影響なし（応答なしの検出が最大 6 秒遅れる） |
| アイコンはパスごとに保存し、更新日時が変わったときだけ読み直す | OS への問い合わせを減らす |
| 変化が無ければ状態を書かない（実行中・インスタンス数・応答なし・再生状態） | SwiftUI の描き直しを防ぐ |
| 再生中ウィジェットが無ければ、取得を一切しない | 使わない機能の費用ゼロ |
| ウィンドウの大きさ変更は `NSAnimationContext` で補間し、中身は SwiftUI の `.animation` | 滑らかな動きを保つ |

### 4.2 測定

`ps -o %cpu` を 1 秒ごとに 20〜30 回取り、`sample` でスタックを取った。

| 時点 | 平均 CPU | 最大 |
|---|---|---|
| 間引き前（再生取得 1.5 秒・応答 3 秒・アイコン 3 秒） | 4.1% | 7.8% |
| 間引き後（再生取得 3 秒・応答 6 秒・アイコン 30 秒） | 3.6% | 9.1% |
| タイマー可変化後（上に加えて widget/ホバーのタイマーを可変に） | 4.0% | 15.4% |
| 帯が隠れている間（更新を停止） | 0.9% | 1.8% |

- 差は小さい。**測定のばらつき（再生中の曲・他のアプリの動き）と同じ程度**で、間引きの効果として断定できない。
- `sample`（間引き前）で目立った処理は、メインスレッドの待ち（イベントループ）を除くと、**再生中の取得（`perl` 起動）が最大**、次にタイマー本体（0.25 秒の判定）、実行中アプリの巡回、応答確認（AX）、アイコンの更新確認の順。
- 間引き後の `sample` では、再生中の取得が目立たなくなり、残りはタイマー本体と実行中アプリの巡回が上位。

### 4.3 残っている最適化（未実施・推測を含む）

| 候補 | 狙い | 見た目への影響 | 状態 |
|---|---|---|---|
| 一時的なアプリを実行中の枠・履歴に出さない（2 秒続くまで待つ） | 標準 Dock と同じ見え方にする（CPU の目的ではない） | なし | 実施済み |
| `widgetTimer` を、秒まで出す時計・日付があるときだけ 0.25 秒に、無ければ 1 秒に | 常時 4 回/秒の起床を減らす | なし | 実施済み。**オーナーの設定（日付が秒まで・自動で隠すがオン）では速いタイマーが必要なため、CPU は減らなかった**（測定 4.0%） |
| 帯が自動で隠れている間は、ウィジェットの更新と再生の取得を止める（出るときにすぐ更新） | 見えないものを更新しない | なし（出た瞬間に最新） | **実施済み。隠れている間の CPU が平均 0.9%（最大 1.8%）に下がった**（30 秒の測定） |
| ホバーの判定を、自動で隠さない設定で帯から離れているときは 0.5 秒に | 帯が見えていない間の起床を減らす | なし | 実施済み。同上（自動で隠すがオンのため 0.2 秒のまま） |
| 再生中の取得で `perl` を起動する代わりに、常駐させる（標準入出力でやり取り） | 起動の費用（プロセス生成）を無くす | なし | 未実施。設計が増えるため、効果を測ってから |
| 再生中の取得を、アプリが再生状態の変化を通知したときだけにする（MediaRemote の通知） | 定期取得をやめる | なし | 未調査 |
| 応答確認を、前面のアプリだけ毎回、他は 30 秒に | AX の呼び出しを減らす | なし | 未実施・推測 |
| CPU の測定を 1 日ぶん取って、時間帯・作業ごとの平均を出す | 測定のばらつきを減らす | － | 未実施 |

2 つのタイマーを可変にしたが、オーナーの設定では減らなかった（秒まで出す日付と「自動で隠す」が速い間隔を要求する）。測定のばらつき（3.6〜4.1%）の範囲で、改善とも悪化とも言えない。
帯が隠れている間の更新停止は実施し、隠れている間は 0.9% まで下がった。**帯が見えている間は 3.6〜4.0% のまま**で、残りは再生中の取得（`perl` 起動）と、秒まで出す日付の更新。再生中の取得の常駐化は、見た目は変わらないが、効果は測っていない。

## 5. リッチな見た目と軽さを両立する考え方

見た目の豊かさ（動き・半透明・グラフ・サムネ）は、**描く回数**と**描く面積**で費用が決まる。次の順で考える。

1. **変化があったときだけ描く。** 状態が同じなら書き込まない。ウィジェットの文・グラフの点・再生位置は、値が変わったときだけ更新する。
2. **見えていないものは更新しない。** 帯が隠れている間、閉じたグループの中、画面外のタイルは更新を止める。
3. **動きは OS に任せる。** `NSAnimationContext` と SwiftUI の `.animation(Motion.spring)` を使う（推測：描画が OS の合成に回り、自前のタイマーより軽い。測っていない）。アニメーションを自前のタイマーで 60fps 回さない。
4. **再生位置のように連続して変わるものは、読む回数と描く回数を分ける。** 読むのは 3 秒に 1 回、進み具合はアプリ側で計算し、描画は 0.5 秒ごとの `TimelineView`（推測：画面に出ている間だけ動く。測っていない）。
5. **半透明（`.ultraThickMaterial`）は面積が大きいほど高い。** 吹き出しは件数に合わせて広げ、最大の高さで止めてスクロールにする（面積に上限を設ける）。影は動かすたびに計算し直すので、ドラッグ中の絵には付けない。
6. **重い取得は裏のキューで、結果だけを主スレッドへ。** `ps`・AX・`perl`・AppleScript は主スレッドで呼ばない。多重に走らないよう、実行中フラグで 1 本に絞る。
7. **見た目を決める値は計算で出す。** 幅・高さ・列の数は純粋関数。測らないので、描き直しも、ずれも起きない。
8. **測ってから削る。** `sample` で上位を見て、重い順に減らす。効果が測定のばらつきより小さい間引きは、見た目を削るほどの理由にならない。

## 6. 検証の方法

- `./tests/run.sh`：純粋関数（配置・当たり判定・解釈・判定）を、画面なしで検査する。`ALL OK` が出れば通過。
- `swiftc -typecheck -target arm64-apple-macos14.0 Sources/*.swift`：型検査。
- 画面の確認：`ImageRenderer` で SwiftUI を画像に書き出して見る。実カーソルは動かさない。
- 検証用の実行ファイルで `Store()` を作らない（起動時の整形で実データの `groups.json` などを書くため）。作るときは保存先を差し替える。検証用のファイルは、フォルダの中の `.build/`（Git の対象外）に置き、終えたら消す（フォルダ内で完結させる。オーナーの指示）。`/tmp` は使わない。

## 7. 既知の制約・未確認

- Unity で作ったゲームの緑丸：Unity エディターの `Info.plist` は `LSBackgroundOnly = true` で、通常のアプリ扱いにならない。起動中の判定を、通常のアプリに限らず動いているアプリ全体に広げた。**実際の Unity ゲームでは確かめていない**（手元に無い）。
- 標準 Dock が全画面アプリで出る件：全画面では待ち時間 1000 秒が効かないと見ている。GroupDock の帯は全画面にも出す。オーナーの確認では「一旦良さそう」。
- **Mission Control（Ctrl+↑）中は標準 Dock が出る。仕様として残す（オーナーの判断）。** 実測：Mission Control が出ている間だけ、Dock が画面ごとに層 18〜20 の窓を作り、Dock 自身が下端に描く。`autohide`・`autohide-delay` は効かない。`tilesize` を 1 まで下げ、拡大を切っても、小さな帯が残り、完全には消えない（元の値は検証後に戻した）。覆う窓で隠す案は、壁紙と色が合わず不自然になりうるため採らなかった。
- 前へ・次へが使える再生元（YouTube の再生リストなど）での実際の動き：未確認。
- システムの再生の音量：MediaRemote には音量が無い。実行中の Chrome・Safari が「同じ題名で再生中」のときだけ、そのタブの音量を付けて読み書きする（`NowPlayingParse.merging`・`volumeTarget`）。見つからなければ灰色にする。別の曲のタブや止まったタブの音量は付けない。実機の YouTube では未確認。
